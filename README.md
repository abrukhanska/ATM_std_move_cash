# std::move(cash) — навчальна система банкомата (C++20)

**std::move(cash)** — консольна модель банкомата з клієнтським і службовим режимами, локальною базою **SQLite**, журналом операцій і автоматизованими тестами. Це завершений груповий проєкт із методів об'єктно-орієнтованого програмування; матеріали архітектури, реалізації та опрацювання рецензій розміщені в `docs/`.

Програма моделює грошові операції, а не взаємодіє з фізичними купюроприймачами, банківськими мережами чи реальними платіжними системами. Інтерфейс — **консольний, англійською мовою**.

## Функціональність

### Клієнтський режим (`CardKind::Client`)

| Пункт | Операція | Поведінка |
| --- | --- | --- |
| `1` | **Balance** | Перегляд балансу вибраного власного рахунку. |
| `2` | **Withdraw** | Зняття готівки: швидкі суми 200, 500, 1000, 2000 грн або власна сума, кратна 100 грн. |
| `3` | **Deposit** | Внесення кількох номіналів купюр за одну операцію з попереднім показом суми й підтвердженням. |
| `4` | **Transfer** | Переказ на основний рахунок іншої картки з попереднім показом імені одержувача. |
| `5` | **Payments** | Мобільні платежі та благодійність; підтримуються суми з копійками. |
| `6` | **Change PIN** | Зміна PIN після перевірки поточного та повторного введення нового. |
| `7` | **Contact support** | Підтверджене звернення записується в `support.log`. |
| `0` | **Cancel** | Завершення клієнтського сеансу й повернення до введення картки. |

Для грошових операцій після успішного виконання пропонується **консольний чек**. Відмова від чека або збій друку після успішного `commit` не скасовує вже здійснену операцію.

### Службовий режим (`CardKind::Service`)

| Пункт | Операція | Поведінка |
| --- | --- | --- |
| `1` | **Cash inventory** | Кількість банкнот кожного номіналу та загальна сума. |
| `2` | **Load cash** | Завантаження набору банкнот у касети. |
| `3` | **Unload cash** | Вилучення доступних банкнот. |
| `4` | **Recent operations** | Останні 20 записів журналу, від новіших до старіших; види операцій відображаються назвами. |
| `5` | **Statistics** | Загальні суми завантаження, внесення та зняття. |
| `6` | **Retained cards** | Перелік затриманих клієнтських карток. |
| `7` | **Release card** | Розблокування затриманої клієнтської картки. |
| `8` | **ATM mode** | Вимкнення або відновлення обслуговування клієнтів. |
| `0` | **Cancel** | Завершення службового сеансу: перехід у `Idle` або `OutOfService` згідно з поточним режимом. |

`OutOfService` (клієнтів тимчасово не обслуговують) **не тотожний** `broken` (несправне сховище). У першому режимі оператор може відновити роботу, якщо сховище справне; за `broken` програма припиняє виконання.

## Вимоги та залежності

- **CMake 3.20+**.
- Компілятор з підтримкою **C++20**: MSVC (Visual Studio 2022), GCC або Clang.
- На Windows для наведених команд — **Visual Studio 2022 Developer PowerShell** і **Ninja** (`Ninja Multi-Config`).
- **Git** для отримання PicoSHA2 через CMake `FetchContent`.
- **Підключення до інтернету при первинній конфігурації** або заздалегідь заповнений кеш `FetchContent`: CMake завантажує PicoSHA2 та вихідний архів SQLite.
- Термінал із підтримкою ANSI-послідовностей бажаний для кольорового оформлення.
- **Часовий пояс середовища має відповідати Києву.** Це важливо для добового ліміту зняття та перевірок переходів на літній/зимовий час.

У кореневому `CMakeLists.txt` **PicoSHA2 закріплено за конкретним Git-комітом**, а в `src/CMakeLists.txt` **SQLite amalgamation — за конкретним URL і SHA-256 архіву**. Таким чином, виправлено ризик рухомої Git-гілки PicoSHA2, на який звернули увагу в рецензії. **Однак залежність першої конфігурації від мережі залишається**: це не повністю автономна збірка. Окремо встановлювати SQLite для стандартної збірки не потрібно.

## Збірка та запуск

> Команди виконуються **з кореня репозиторію**, де лежить головний `CMakeLists.txt`. Не змішуйте різні генератори CMake в одній і тій самій папці `build/`.

### Windows — Visual Studio 2022 Developer PowerShell

Виконайте кожну команду **після завершення попередньої**:

```powershell
cmake -S . -B build -G "Ninja Multi-Config"
cmake --build build --config Debug --parallel
ctest --test-dir build -C Debug --output-on-failure
cmake --build build --config Release --parallel
ctest --test-dir build -C Release --output-on-failure
```

Після збирання запуск Debug:

```powershell
.\build\src\Debug\atm_main.exe
```

Або Release:

```powershell
.\build\src\Release\atm_main.exe
```

Альтернатива з генератором Visual Studio: `cmake -S . -B build -G "Visual Studio 17 2022"`, потім `cmake --build build --config Debug` або `Release`. Використовуйте цю альтернативу **лише в новому/очищеному каталозі збірки**, не поверх наявної конфігурації Ninja.

**Часовий пояс Windows:** в налаштуваннях дати та часу Windows виберіть часовий пояс Києва з автоматичним переходом на літній/зимовий час. Середовище перевіряється окремим тестом `atm_environment_tests`.

### Linux / macOS

Потрібні CMake, компілятор C++20, Git та стандартний засіб збирання (Make або Ninja — залежно від генератора):

```bash

TZ=Europe/Kyiv ctest --test-dir build --output-on-failure
```

Тут показано **одноконфігураційну** збірку. На відміну від Windows-команд вище, виконуваний файл не лежить у підкаталозі `Release/`.

### Чиста демонстраційна база без втрати наявних даних

`atm.db` створюється **в поточному робочому каталозі**, а не обов'язково поряд із виконуваним файлом. Для захисту зручно запустити банкомат в окремій новій папці. У Windows PowerShell із кореня проєкту, **після Debug-збірки**:

```powershell
$exe = (Resolve-Path ".\build\src\Debug\atm_main.exe").Path
$demo = Join-Path (Split-Path (Get-Location).Path -Parent) ("ATM_demo_" + (Get-Date -Format "yyyyMMdd_HHmmss"))
New-Item -ItemType Directory -Path $demo | Out-Null
Push-Location $demo
& $exe
Pop-Location
```

Для перевірки збереження даних повторно запустіть `$exe` **із тієї самої `$demo`**, а не з нової папки. Початкова база проєкту не зачіпається.

## Демонстраційні дані

На порожній базі `seedDemoDataIfEmpty` створює наведені записи. **Наявну заповнену базу запуск не скидає**: змінений PIN і виконані операції зберігаються після перезапуску.

| Картка | Тип | Власник | Демонстраційний PIN | Рахунки |
| --- | --- | --- | --- | --- |
| `4000000000000001` | Client | Alice | `1234` | №1 (основний) — **20 000 грн**; №2 — **5 000 грн** |
| `4000000000000002` | Client | Bob | `5678` | №3 (основний) — **15 000 грн** |
| `4000000000000003` | Service | Operator | `9999` | Без клієнтських рахунків |

Мобільні отримувачі: **Vodafone Ukraine, Kyivstar, lifecell**. Благодійні отримувачі: **Come Back Alive, UNITED24**. Довідник задано у `PaymentService`, не завантажується з банківського API.

> Ці PIN призначені **лише для навчальної демонстрації**. Якщо на вже використаній базі PIN змінювали, потрібен новий PIN або нова порожня демонстраційна база.

## Керування та приклад сценарію

- У меню вводьте номер пункту (`1`, `2` тощо). **`0` означає `Cancel` у поточному меню**, але наслідок залежить від контексту: у головному меню клієнта/оператора це завершення сеансу, у вкладеному діалозі — скасування вибору.
- Текстові команди `cancel` і `exit` розпізнаються незалежно від регістру та зовнішніх пробілів. `cancel` скасовує поточну дію; `exit` завершує відповідний сеанс або програму на стартовому екрані.
- На підтвердження вводьте `yes`, для відмови — `no`.
- Номер картки: **16 цифр**, PIN: **4 цифри**. Зовнішні пробіли в номері картки допускаються функцією `parseCardNumber`; вимоги до PIN не послаблюються.
- Перекази та платежі приймають **додатні суми з максимум двома знаками після крапки або коми**, наприклад `100.50` чи `100,50`. Зняття приймає лише додатні суми, **кратні 100 грн**.
- У разі некоректного значення інтерфейс показує причину та, де це передбачено діалогом, пропонує повторити введення.

### Короткий сценарій, що показує алгоритм підбору купюр

На **новій порожній демонстраційній базі**:

1. Увійдіть оператором `4000000000000003` / `9999`.
2. **Service menu → `2` Load cash**. Введіть послідовно кількості для 100 / 200 / 500 / 1000 / 2000 грн: **`0`, `3`, `1`, `0`, `0`**. Підтвердіть `yes`. У касетах буде **1100 грн**.
3. Завершіть службовий сеанс через `0`.
4. Увійдіть як Alice: `4000000000000001` / `1234`, оберіть рахунок №1.
5. **Client menu → `2` Withdraw → `5` Enter custom amount → `600` → `yes`**.
6. Очікуваний результат: **3 купюри по 200 грн**, баланс Alice — **19 400 грн**, залишок касет — **500 грн**.

Чому це нетривіально: жадібний вибір купюри 500 грн залишає 100 грн, яких немає. `planDispense` повертається до іншої комбінації й знаходить **200 + 200 + 200**. Це ілюструє **backtracking**, а не глобальну мінімізацію кількості купюр.

### Інші важливі сценарії

- Після зняття 200 грн спроба зняти **150 грн** відхиляється через некратність 100 грн.
- Якщо баланс недостатній, ліміт перевищено чи потрібної готівки немає, відображаються **різні причини відмови**.
- Змішане внесення `2 × 100 + 1 × 500` становить **700 грн** і виконується лише після підтвердження.
- Переказ на власну картку заборонений; переказ іншому клієнту спрямовується на його основний рахунок.
- Благодійний платіж не вимагає номера телефону чи іншого реквізиту; для мобільного платежу потрібні рівно 10 цифр.

## Основні правила

| Правило | Реалізація |
| --- | --- |
| Клієнтський PIN | Після третьої неправильної **коректно сформатованої** спроби картка стає `Retained`. Успішна автентифікація скидає лічильник. |
| Службова картка | Лише `Active` з лічильником 0; конструктор `Card` відхиляє некоректну комбінацію. Три неправильні PIN завершують поточну спробу входу, але не затримують картку. |
| Власність рахунків | Сервіси перевіряють власника рахунку незалежно від вибору в меню. |
| Добовий ліміт | **10 000 грн на картку за календарну добу Києва**, сумарно за її рахунками; рахується за збереженим журналом знять. |
| Порядок відмов зняття | Після перевірок суми й доступу: **баланс → добовий ліміт → можливість видати купюри** (W2). |
| Підбір купюр | Точна сума з доступних номіналів, перевага більшим купюрам із поверненням, якщо жадібний вибір не спрацював (W3). |
| Номінали | **100, 200, 500, 1000, 2000 грн**. Кількість кожного номіналу зберігається в `uint32_t`, із перевіркою переповнення; фізичну місткість касет не моделюємо. |
| Внесення | Рахунок, касети й журнал оновлюються в межах однієї транзакції. |
| Переказ | На основний рахунок іншої картки; ім'я показується до підтвердження, умови повторно перевіряються під час виконання. |
| Платежі | Для мобільного платежу потрібен 10-цифровий номер; для благодійності реквізит порожній. |
| Повернення з операції | Після успішного `commit` скасування в меню або несправний принтер **не відкочують** фінансову операцію. |

## Архітектура та гарантії

```text
                        main.cpp
             (створення об'єктів і запуск)
                 /        |          \
                v         v           v
       presentation   application   infrastructure
        (UI, State)    (сервіси)     (SQLite)
              |  \      |             |
              |   ------v             |
              +------> domain <-------+
                   (типи, інтерфейси)
```

- **`domain/`** — типи `Money`, `BanknoteSet`, `CardNumber`, `PinCode`, сутності `Card`, `Account`, `JournalEntry`, правила, `IStorage`, інтерфейси репозиторіїв і `Transaction`.
- **`application/`** — бізнес-операції: `AuthService`, `AccountService`, `WithdrawalService`, `DepositService`, `TransferService`, `PaymentService`, `CashService`, `MonitoringService`, `CardAdministrationService`, `DeviceService`, `planDispense`, `PinHasher`.
- **`infrastructure/sql/`** — реалізація `IStorage` через SQLite (`Database`, репозиторії, `data_seeder.cpp`, спільний RAII-помічник підготовлених SQL-запитів `stmt.hpp`).
- **`presentation/`** — `AtmMachine`, `AtmState`, `IdleState`, `ClientState`, `ServiceState`, `OutOfServiceState`, `ConsoleUi`, діалоги, друк чеків і `LoggingSupportChannel`.

Сервіси `application` **не звертаються безпосередньо до SQLite**: вони працюють через інтерфейси `domain::IStorage` і репозиторіїв. Це дозволяє застосовувати реальне SQL-сховище та тестовий `TestStorage` для перевірки бізнес-правил. `TestStorage` **не дублює всі SQL-обмеження** реальної бази, проте виконує потрібні для тестів контракти (включно з валідацією `JournalEntry` та відкатом знімка стану).

- **State:** `AtmMachine` володіє поточним `std::unique_ptr<AtmState>` та змінює поведінку переходами між станами. Меню не є місцем зберігання банківських правил.
- **RAII:** `Transaction` володіє *межами транзакції* й позичає `IStorage&`. Якщо не стався успішний `commit`, деструктор викликає `rollback()`.
- **SQLite:** `Database` володіє з'єднанням через `std::unique_ptr<sqlite3, SqliteCloser>`, яке оголошено перед репозиторіями, тому живе довше за них. Підготовлені SQL-запити звільняються RAII-помічником `Stmt` із `stmt.hpp`. `BEGIN IMMEDIATE` відкриває транзакцію, встановлено `sqlite3_busy_timeout(5000)`.
- **Відмови:** за невдалого відкату `Database` переходить у `broken`; стан сховища не слід ототожнювати з перемиканням `ATM mode`. Передбачено завершення роботи й одноразову спробу повідомлення каналу підтримки.
- **Друк чека:** після `commit`, щоб помилка консолі/принтера не призводила до повторення вже підтвердженої операції.

`ST2` перевіряє **задекларовані правила прямих `#include`-залежностей** між шарами; це не повна формальна перевірка всієї архітектури чи транзитивних залежностей.


**Спочатку обов'язково зберіть потрібну конфігурацію** (`cmake --build build --config Debug` або `Release`), інакше CTest може не знайти виконувані файли або запустити старі збірки.

Основні групи перевірок: W1–W4 (зняття й ліміт), W3 (`planDispense` та незалежний еталон), D1 (внесення), TR1–TR2 (переказ), P1 (платежі), SV1–SV5 (службовий режим), X1–X3 (відкати, транзакції та БД), X4 (збої друку), SEC1 (чутливі дані), ST2 (прямі залежності).

## Зберігання даних і повторний запуск

| Файл | Призначення |
| --- | --- |
| `atm.db` | Локальна база SQLite із таблицями `cards`, `accounts`, `banknotes`, `journal`; створюється у поточній робочій теці. |
| `support.log` | Локальний журнал звернень до підтримки; потік відкривається в режимі дописування під час запуску. |

Обидва типи файлів виключені з Git через `.gitignore`.

Щоб **побачити збереження даних**, виконайте операцію, завершіть програму і запустіть її знову в **тій самій робочій теці**. Перевірте баланс, склад касет або журнал; новий запуск не скидає непорожню БД.

Щоб **почати з нуля**, найкраще запустити виконуваний файл з іншої порожньої папки. Якщо видаляєте `atm.db`, робіть це **лише після резервного копіювання та після завершення програми**; видалення безповоротно скине дані цієї демонстраційної бази.

Режим `inService` у поточній моделі є **станом об'єкта `DeviceService` у пам'яті** та під час нового запуску ініціалізується значенням `true`; запис про його зміну потрапляє до журналу, але сам прапорець не відновлюється з SQLite. Не слід ототожнювати це з постійною фізичною конфігурацією обладнання.

## Захист даних та межі моделі

- У SQLite зберігаються **хеші**, а не PIN відкритим текстом: власна навчальна схема `sha256$iterations$salt$hash` із 16-байтовою випадковою сіллю та 10 000 ітераціями SHA-256 за замовчуванням. **Це не PBKDF2/Argon2 і не банківський стандарт.**
- Повний PIN не додається до журналу операцій, чека чи запису звернення до підтримки. Номери карток у чеках маскуються.
- `ConsoleUi::promptSecret()` зараз викликає звичайний `prompt()` — **цифри PIN видно під час введення**. Приховування введення на рівні термінала не реалізовано.
- Для службової картки після трьох неправильних PIN завершується **поточна спроба входу**; між окремими входами лічильник не зберігається. Це обмеження навчальної моделі.
- `localDay()` використовує **системний локальний час**, а не вбудовану незалежну базу часових поясів: правильність київської доби залежить від конфігурації середовища. Тести перевіряють зимовий і літній час.
- Програма працює в одному потоці. Міжпроцесні гарантії одночасної авторизації в декількох екземплярах банкомата не заявляються.
- Немає фізичних лімітів місткості касет, контролю реального приймання/видачі банкнот, мережевого банкінгу, комісій, кредитів, NFC, зняття без картки, інших валют, міжбанківських переказів і зовнішніх API.

## Типові проблеми під час запуску

| Симптом | Перевірте |
| --- | --- |
| `No tests were found` | Чи виконано успішну конфігурацію CMake (`cmake -S . -B build ...`), чи тестуєте правильний каталог. |
| `Could not find executable` у CTest | Чи зібрано **саме цю** конфігурацію (`Debug`/`Release`) перед запуском тестів. |
| Завантаження PicoSHA2/SQLite завершується помилкою | Інтернет, Git, доступ до GitHub і sqlite.org, проксі; під час першого `FetchContent` мережа потрібна. |
| `atm_environment_tests` падає на Windows | Системний часовий пояс і автоматичне переведення часу мають відповідати Києву. |
| Після запуску баланс уже змінений або не працює `1234` | Ви повторно відкрили існуючу `atm.db`. Використайте окрему чисту демонстраційну теку. |
| Зняти готівку неможливо відразу після першого запуску | Початкові касети порожні; спочатку виконайте `Load cash` службовою карткою. |
| Кольорові рамки відображаються некоректно | Використовуйте термінал із підтримкою ANSI. |
| Повідомлення `ATM fatal error` або помилка відкриття сховища | Перевірте права запису у поточній теці та цілісність/доступність `atm.db`; не змінюйте її під час роботи програми. |
