# std::move(cash) — Банкомат на C++20

Консольна модель банкомата з клієнтським і службовим режимами. Проєкт команди **std::move(cash)**, завдання T1 «Архітектура банкомата».

Програма працює в одному потоці, зберігає дані в локальній базі SQLite і не підключається до жодного реального обладнання чи платіжних систем: видача та внесення готівки моделюються зміною балансу й кількості купюр у касетах.

## Можливості

**Клієнтський режим** (картка типу `Client`):

| Операція | Опис |
| --- | --- |
| Balance | Баланс обраного рахунку |
| Withdraw | Зняття готівки: швидкі суми 200 / 500 / 1000 / 2000 грн або власна сума |
| Deposit | Внесення купюр із підтвердженням |
| Transfer | Переказ за номером картки одержувача з попереднім показом його імені |
| Payments | Оплата послуг: мобільний зв'язок і благодійність |
| Change PIN | Зміна PIN (поточний і двічі новий) |
| Contact support | Звернення до підтримки (записується у `support.log`) |

Після успішної фінансової операції користувачу пропонується чек, який друкується в консоль.

**Службовий режим** (картка типу `Service`):

| Пункт меню | Опис |
| --- | --- |
| Cash inventory | Кількість купюр у касетах |
| Load cash / Unload cash | Інкасація: завантаження та вилучення купюр |
| Recent operations | Останні 20 записів журналу |
| Statistics | Загальні суми завантажень, внесень і знять |
| Retained cards | Список затриманих карток |
| Release card | Розблокування затриманої клієнтської картки |
| ATM mode | Вивід банкомата з обслуговування та повернення в роботу |

## Швидкий старт

### Вимоги

- **CMake 3.20+**
- Компілятор із підтримкою **C++20** (MSVC, GCC або Clang)
- Доступ до інтернету під час першого налаштування проєкту: CMake сам завантажить
  [PicoSHA2](https://github.com/okdshin/PicoSHA2) (SHA-256) та вихідні коди SQLite
  (amalgamation, із перевіркою SHA-256 архіву)
- Термінал із підтримкою ANSI-кольорів (Windows Terminal, PowerShell 7, термінали Linux/macOS)

Окремо встановлювати SQLite не потрібно.

### Збірка

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
```

Для Visual Studio достатньо відкрити теку проєкту як CMake-проєкт.

### Запуск

Програма створює `atm.db` і `support.log` у **поточній теці**, тому запускайте її з тієї теки, де ці файли мають лежати.

Linux / macOS:

```bash
TZ=Europe/Kyiv ./build/src/atm_main
```

Windows (PowerShell):

```powershell
.\build\src\Release\atm_main.exe
```

> **Часовий пояс.** Добовий ліміт зняття рахується за календарною добою **Києва** за системним локальним часом. Тому на Windows у системі має бути встановлений київський часовий пояс, а на Linux/macOS — запускати з `TZ=Europe/Kyiv`.

### Перший сценарій

Після першого запуску **касети порожні**, тож зняти готівку неможливо, доки оператор не завантажить купюри:

1. Введіть картку оператора `4000000000000003`, PIN `9999`.
2. Оберіть **Load cash**, вкажіть кількість купюр кожного номіналу й підтвердіть.
3. Вийдіть із сервісного меню (`0`) і увійдіть карткою клієнта `4000000000000001` з PIN `1234`.
4. Оберіть рахунок і виконайте операцію, наприклад **Withdraw**.

## Демонстраційні дані

Якщо база порожня, при першому запуску вона наповнюється демонстраційними даними. Наявну базу програма не перезаписує.

| Картка | Тип | Власник | PIN | Рахунки |
| --- | --- | --- | --- | --- |
| `4000000000000001` | Client | Alice | `1234` | №1 (основний) — 20 000 грн; №2 — 5 000 грн |
| `4000000000000002` | Client | Bob | `5678` | №3 (основний) — 15 000 грн |
| `4000000000000003` | Service | Operator | `9999` | немає |

Довідник отримувачів платежів задається в коді (`PaymentService`):

| Категорія | Отримувачі |
| --- | --- |
| Мобільний зв'язок | Vodafone Ukraine, Kyivstar, lifecell |
| Благодійність | Come Back Alive, UNITED24 |

Щоб почати з чистого стану, видаліть `atm.db`.

## Керування в консолі

- Меню обираються цифрою пункту; `0` означає **Cancel** (повернення на крок назад).
- У будь-якому полі введення можна написати `cancel` (скасувати поточну дію) або `exit` (завершити сеанс; на початковому екрані — вийти з програми).
- Кінець вводу (EOF, `Ctrl+D` / `Ctrl+Z`) обробляється як `exit`.
- Інтерфейс програми англійською.

## Бізнес-правила

- **Вхід клієнта:** номер картки з 16 цифр і PIN із 4 цифр. Після **третього** хибного PIN картка затримується. Лічильник спроб зберігається для кожної картки й скидається після успішного входу або розблокування оператором.
- **Вхід оператора:** після трьох хибних спроб вхід завершується, картка не затримується, лічильник між входами не зберігається.
- **Зняття:** додатна сума, кратна 100 грн. Перевірки йдуть у порядку: достатність коштів → добовий ліміт → наявність купюр. Для різних причин відмови показуються різні повідомлення.
- **Добовий ліміт:** 10 000 грн на картку сумарно за всіма її рахунками за календарну добу Києва; рахується із журналу.
- **Видача купюр:** алгоритм `planDispense` спершу пробує великі номінали, а якщо точна сума так не набирається — перебирає інші комбінації. Номінали: 100, 200, 500, 1000, 2000 грн.
- **Переказ:** надходить на основний рахунок картки одержувача. Переказ на власну картку (включно з іншими власними рахунками) заборонений. На затриману картку іншого клієнта переказ дозволений.
- **Оплата:** для мобільного платежу потрібен номер із 10 цифр; для благодійності додаткові реквізити не потрібні. Кошти лише списуються, а в журнал додається запис.
- **Зміна PIN:** новий PIN не може збігатися зі старим.
- **Атомарність:** баланс, касети й журнал оновлюються в **одній транзакції**. Після успішної операції скасувати її через меню не можна.
- Усі суми в гривнях, без комісій. У коді вони зберігаються цілими копійками.

Ліміти, номінали купюр, кратність суми зняття й кількість спроб PIN через меню не змінюються.

## Архітектура

Проєкт поділений на чотири шари. Залежності спрямовані лише вниз; `main.cpp` створює всі об'єкти й передає залежності посиланнями.

```
┌─────────────────────────────────────────────┐
│  main.cpp  (складання об'єктів, меню)       │
└─────────────────────────────────────────────┘
        │              │               │
        ▼              ▼               ▼
┌──────────────┐ ┌─────────────┐ ┌────────────────┐
│ presentation │ │ application │ │ infrastructure │
│ меню, стани, │ │ сервіси     │ │ SQLite-        │
│ діалоги, UI  │ │ операцій    │ │ репозиторії    │
└──────┬───────┘ └──────┬──────┘ └───────┬────────┘
       │                │                │
       └────────►┌──────▼──────┐◄────────┘
                 │   domain    │
                 │ типи, правила│
                 │ інтерфейси  │
                 └─────────────┘
```

| Шар | Простір імен | Відповідальність |
| --- | --- | --- |
| `domain` | `atm::domain` | Значення (`Money`, `BanknoteSet`, `CardNumber`, `PinCode`), сутності (`Card`, `Account`, `JournalEntry`, `Payee`), правила, інтерфейси сховища (`IStorage`, `I*Repository`) і RAII-клас `Transaction`. Залежить лише від стандартної бібліотеки |
| `application` | `atm::application` | Сервіси операцій: `AuthService`, `AccountService`, `WithdrawalService`, `DepositService`, `TransferService`, `PaymentService`, `CashService`, `MonitoringService`, `CardAdministrationService`, `DeviceService`; `planDispense`, `PinHasher`. Працюють зі сховищем лише через `IStorage` |
| `infrastructure` | `atm::infrastructure::sql` | Реалізація сховища на SQLite: `Database`, репозиторії, `StorageError`, наповнення демо-даними й перевірка цілісності бази. Увесь SQL — лише тут |
| `presentation` | `atm::presentation` | Консольний UI (`ConsoleUi`), друк чека, канал підтримки (`support.log`), діалоги операцій, сеанси та стани банкомата |

### Ключові рішення

- **Стани банкомата** (`AtmState`): `IdleState` → `ClientState` / `ServiceState`, а також `OutOfServiceState`, коли обслуговування клієнтів вимкнене. Стани заміщують один одного через `std::unique_ptr`.
- **Транзакції:** `Transaction` на стеку сервісу викликає `rollback()` у деструкторі, якщо не було успішного `commit()`. `Database::begin()` виконує `BEGIN IMMEDIATE`.
- **Повернення за значенням:** результати читання з бази не посилаються на буфери SQLite.
- **Керування ресурсами:** з'єднання SQLite й запити тримаються в `unique_ptr` із власними deleter-ами; `Database`, `Transaction`, `AtmContext` та `AtmMachine` не копіюються й не переміщуються.
- **Помилки:** порушення правил операцій — `DomainError` з причиною `ErrorReason`; технічні збої бази — `StorageError`; неправильний формат значень у `parse` — `std::invalid_argument`.
- **Несправна база:** якщо відкат не вдався, сховище позначається як `broken`, сеанс завершується, звичайні запити блокуються до перезапуску.

## Тести

Тести написані на власному мінімалістичному фреймворку (`tests/support/mini_test.hpp`) і збираються разом із проєктом. Є п'ять тестових виконуваних файлів:

| Виконуваний файл | Що перевіряє |
| --- | --- |
| `atm_domain_tests` | Значення, сутності, правила domain |
| `atm_environment_tests` | Налаштування середовища, зокрема часовий пояс |
| `atm_application_tests` | Сервіси, `planDispense`, хешування PIN |
| `atm_infrastructure_tests` | Репозиторії SQLite, транзакції, відкат, фінансові сценарії на реальній базі |
| `atm_presentation_tests` | Консольний UI, чек, канал підтримки |

Окремо компілюється перевірка того, що кожен заголовок `domain/*.hpp` самодостатній (`atm_domain_header_check`).

Запуск:

```bash
ctest --test-dir build -C Release --output-on-failure
```

На Linux/macOS тест середовища автоматично запускається з `TZ=Europe/Kyiv`. На Windows пояс має бути налаштований у системі.

## Безпека PIN-кодів

- У базі зберігається лише хеш у форматі `sha256$<ітерації>$<сіль>$<хеш>`: 16-байтова випадкова сіль і 10 000 ітерацій SHA-256, усе в шістнадцятковому записі.
- Введений PIN не потрапляє до журналу, чека чи повідомлень підтримці.
- Повідомлення `StorageError` не містять PIN, хеша, значень SQL-параметрів і повних номерів карток; на чеку номер картки маскується.

Це навчальний проєкт: захист рівня банківської системи, апаратна криптографія, приховування введення PIN у терміналі й гарантоване стирання PIN із пам'яті до його складу не входять.

| Файл | Призначення |

| `atm.db` | База SQLite: таблиці `cards`, `accounts`, `banknotes`, `journal` |

## Що не входить до проєкту

Кредити, NFC, зняття без картки, іноземні валюти, зовнішні перекази, мережа банкоматів, комісії, фізична місткість касет, часткова видача купюр, поломки обладнання й мережеві затримки. Створення карток і рахунків через меню не передбачене — вони задаються початковими даними.
